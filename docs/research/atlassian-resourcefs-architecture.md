# Atlassian ResourceFS architecture research

## Question and scope

This note answers: **where would a multi-site Atlassian source fit in the current ResourceFS architecture, and where would it conflict with existing seams?** It traces the repository's source registration, Server Profile and credential path, typed references and canonical identity, aggregate/field/creation projections, discovery and continuation rules, mutation authority and revalidation, degraded-source behavior, deterministic upstreams, and live smoke entry points.

The evidence is the current ResourceFS repository, with GitHub and generic HTTPS as the concrete remote-source precedents. **External Atlassian API research is intentionally out of scope.** No Atlassian endpoint names, object shapes, authentication rules, or pagination semantics are assumed below. Any such behavior is called out as a live/design question rather than inferred from the existing GitHub adapter.

## Executive answer

A multi-site Atlassian source should fit the existing **compiled Source Adapter** model, not be treated as an unstructured HTTPS document source. The reusable shape is:

- `resourcefs-core::SourceAdapter` for reads, `DiscoveryAdapter` for search/glob decisions, and `MutationAdapter` only if the source exposes mutation;
- the shared `resourcefs-sources::http::HttpSubstrate` for bounded HTTPS egress, redirects, address policy, credentials, status transport, and cancellation;
- a strict tagged Server Profile variant converted to validated source configuration before launch;
- typed `PathReference` address variants and newtypes for site/object/child identities;
- source-owned rendering and validation, with the core read/discovery/mutation engines retaining common limits, recovery, snapshots, locks, error categories, and operation journaling.

GitHub demonstrates the full remote-object pattern: read-only Aggregates link to independently addressable authoritative Fields; collection and Aggregate rendering carry canonical child references; page continuations are typed; upstream identities and parent URLs are checked before rendering; and mutations use source grants, uncached authoritative preflight, content-derived Version Tags, and response validation. HTTPS demonstrates the lower-level network boundary and is deliberately read-only.

The main architectural decision is **where site identity and authority live**. The current profile permits at most one source definition per `kind`, gives GitHub one source-wide credential and repository-level nested grants, and uses a source key plus canonical reference for mutation serialization. A multi-site Atlassian design therefore needs an explicit site identity in both the typed address and authority model, and must decide whether one `atlassian` source owns all sites (with per-site state/credentials/grants) or whether the profile model is changed to allow multiple instances. The existing one-kind rule makes the latter unavailable without a contract change; silently adding a second convention would be incorrect.

A second decision is availability granularity. `required` and `degraded` are currently source-level. One source containing several sites cannot express “site A is degraded while site B remains available” without defining a site-level availability model; otherwise one failed site either makes the complete source unavailable or is silently hidden. The current HTTP substrate can already keep degraded origins separate from healthy origins, but the profile and probe records identify sources, not arbitrary child sites.

## Evidence by decision criterion

### 1. Source registration is a closed, compiled registry

`resourcefs-sources/src/compiled.rs` defines `CompiledSources` with filesystem, artifacts, local scratch, and optional HTTPS and GitHub adapters. `CompiledSources::new` builds the namespace catalog from `SourceCatalogMetadata`; `catalog_metadata` appends optional remote adapters only when mounted. `SourceAdapter::read` dispatches by the exhaustive `ResourceAddress` enum, and `DiscoveryAdapter::search` dispatches the same way. Mutation routing is also explicit: filesystem, local, and GitHub source keys are mapped in `mutation_adapter_for`; HTTPS is mounted but returns `unsupported_mutation`; an absent GitHub adapter returns `source_unavailable` ([`compiled.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-sources/src/compiled.rs#L18-L114), [`compiled.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-sources/src/compiled.rs#L116-L229)).

The MCP launch path is equally explicit. `resourcefs-mcp/src/launch.rs` has `COMPILED_PROFILE_SOURCE_KINDS = &["https", "github"]`; an uncompiled configured kind fails launch before a probe verdict is acted upon. `LaunchPlan::from_checked_profile` derives degraded IDs from the one probe run, constructs the filesystem adapter, and mounts HTTPS and GitHub ([`launch.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-mcp/src/launch.rs#L16-L21), [`launch.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-mcp/src/launch.rs#L38-L141)).

`resourcefs-sources/src/catalog.rs` is the catalog seam. `SourceCatalogMetadata::catalog_entries` must provide at least one scheme description; `NamespaceCatalog::source_document` sorts entries, rejects duplicate scheme labels, validates one-line fields, and requires each example to parse as a `PathReference` ([`catalog.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-sources/src/catalog.rs#L16-L59), [`catalog.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-sources/src/catalog.rs#L89-L182)).

**Implication for Atlassian:** a source is a compiled internal module, not a dynamically loaded plugin and not merely a profile URL. Registering a new family would necessarily touch the existing enum/dispatch/catalog/launch seams. The contract already provides the right extension point, but it is intentionally exhaustive so all read, discovery, mutation, and catalog decisions are visible at compile time. A source kind, scheme set, and canonical example must be chosen explicitly; no generic “site map” is currently inferred from profile data.

### 2. Server Profile parsing and credential resolution are strict and staged

`ProfileDocument` is a single strict JSON document with `schemaVersion`, optional workspace/limits/session/logging settings, and an optional bounded source list. `serde(deny_unknown_fields)` and bounded deserializers reject unknown fields, explicit nulls where the field is optional-but-non-null, and overlarge collections. `ProfileDocument::decode` validates schema version, derives validated limits/storage/logging, validates the profile, creates static source metadata, and converts owned source configuration ([`model.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-mcp/src/profile/model.rs#L84-L137), [`model.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-mcp/src/profile/model.rs#L156-L249)).

`SourceProfile` is a tagged closed enum. Current variants are `https`, `github`, `ssh`, `documents`, `skills`, `rules`, `memory`, `vault`, `agentExport`, and `downstreamMcp`. `HttpsSourceProfile` owns an origin list and optional per-origin credential header; `GithubSourceProfile` owns one optional API base URL, one source credential, a private-network flag, and an allowlist of repositories with nested grants ([`model.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-mcp/src/profile/model.rs#L850-L941)).

`validate_profile` validates configuration IDs, permits at most 256 top-level sources, rejects duplicate IDs, and currently rejects more than one source of the same `kind`. Source-specific grant support is checked separately ([`validate.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-mcp/src/profile/validate.rs#L9-L62)). `SourceProfile::mutation_support` records source-kind capability (`GITHUB` is create/update/no-delete; HTTPS is read-only), and `validate_grants` checks parent and nested GitHub/Vault grants ([`model.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-mcp/src/profile/model.rs#L1377-L1477); [`grants.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-sources/src/configuration/grants.rs#L3-L81)).

Conversion is a distinct boundary. `convert_sources` maps each profile variant into a validated `ConfiguredSource`; HTTPS origins become `HttpsOrigin` values and GitHub repositories become `GithubRepository` values. Credentials remain `SecretReference`s, not plaintext values ([`convert.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-mcp/src/profile/convert.rs#L22-L101)). `GithubConfig::new` validates its ID, source grants, repository count, HTTPS API base, nested grant subsets, and case-insensitive repository uniqueness ([`github.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-sources/src/configuration/github.rs#L11-L126)). HTTPS uses non-overlapping validated URL prefixes and validates credential header names against HTTP token/routing rules ([`https.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-sources/src/configuration/https.rs#L8-L184)).

Secret handling has two phases. `StaticChecker` validates environment references and command executables during profile checking, retains resolved environment values only as `Secret`s for redaction, and defers command-backed secrets. `CheckedProfile::probe_targets` resolves deferred secrets before creating a probe target; a failed optional dependency becomes a degraded probe outcome, while a required one fails. It never puts the resolved value in a diagnostic ([`check.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-mcp/src/profile/check.rs#L85-L150), [`check.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-mcp/src/profile/check.rs#L269-L423)). The source-level resolver accepts environment or direct-argv helper references, normalizes one trailing newline from helper stdout, and maps failures to bounded categories without retaining output ([`secret.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-sources/src/secret.rs#L20-L133)).

Mounting is the only launch path that produces a usable `Secret`. `mount_https` resolves each healthy origin's configured credential and builds `OriginCredential`; degraded origins are kept aside and do not resolve credentials. `mount_github` currently requires exactly one GitHub config, resolves its one credential, applies it as `Authorization: Bearer`, and builds one shared substrate ([`profile/mod.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-mcp/src/profile/mod.rs#L113-L214), [`profile/mod.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-mcp/src/profile/mod.rs#L216-L266)).

**Reusable seam:** strict source configuration, deferred/opaque secret references, direct-argv helper isolation, redaction, and per-origin credential attachment. **GitHub-specific assumption:** one source-wide credential and one API origin. A multi-site Atlassian source must choose whether credentials are source-wide, site-specific, or origin-specific and ensure the choice is represented before `Secret` creation. It must also choose whether an optional source's credential failure degrades the entire source or only one site.

### 3. HTTPS egress is reusable; HTTPS document semantics are not an object adapter

`resourcefs-core::AllowedOrigin`, `OriginAllowlist`, and `AddressPolicy` are source-neutral policy values. An origin matches scheme, host, port, and segment-aware path prefix; a private-network grant is separate from allowlisting. Restricted resolved addresses are refused unless the origin grants private-network access ([`http_policy.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-core/src/http_policy.rs#L157-L316)).

`resourcefs-sources/src/http/mod.rs` is the one bounded HTTP egress point. Its request/response types are source-neutral; the substrate authorizes the initial URL and each redirect, covers both DNS names and IP literals, preserves hostname-bound TLS verification while pinning the authorized address, applies fetch/metadata ceilings, and threads `OperationGuard` cancellation. `credentialed` attaches the credential only when the owning origin's `authorizes` predicate matches. Mutation requests use a no-redirect client ([`http/mod.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-sources/src/http/mod.rs#L546-L665), [`http/mod.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-sources/src/http/mod.rs#L668-L849), [`http/mod.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-sources/src/http/mod.rs#L878-L971)).

`HttpsSource` consumes this substrate for reader-mode Markdown or `:raw` text, status classification, line selection, and search. It does not implement mutation, and it deliberately cannot enumerate a remote origin with `glob` ([`https.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-sources/src/https.rs#L16-L25), [`https.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-sources/src/https.rs#L31-L121), [`https.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-sources/src/https.rs#L143-L220)).

**Implication for Atlassian:** reuse `HttpSubstrate`, not `HttpsSource`'s document projection. A typed remote object source needs its own JSON decoding, canonical identity checks, rendering, collection paging, and mutation behavior while still using the single audited egress path. A second HTTP client or source-specific DNS/redirect policy would conflict with the architecture contract.

### 4. Path References are parsed once into typed identity plus projection

`PathReference` stores the caller spelling, a typed `ResourceAddress`, an optional typed `ProjectionSelector`, and explicit competing selector candidates for workspace/local literal-vs-selector ambiguity. Parsing first recognizes catalog, artifact, HTTPS, issue, pull-request, local, and workspace families. `PathReference::canonical`, `issue`, and `pull_request` are constructors that round-trip through the same parser ([`reference.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-core/src/reference.rs#L789-L905), [`reference.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-core/src/reference.rs#L969-L1105)).

Projections are typed as raw, line ranges, or positive page offsets. The accepted spelling is retained, but consumers match `ProjectionKind` accessors rather than reparsing strings ([`reference.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-core/src/reference.rs#L648-L770)). GitHub uses `:page:<n>` for an upstream page; the parser itself does not make that page meaningful—the GitHub adapter does.

`ResourceAddress` is an exhaustive sum with separate `Https`, `Issue`, and `PullRequest` variants. GitHub parsing creates `IssueAddress`/`PullRequestAddress` and nested resource enums for Aggregate, title/body/comments, stable child IDs, reviews, review comments, and diff files. `GithubRepositoryIdentity` validates one ASCII `owner/repository`, canonicalizes ASCII case, and rejects empty, traversal-like, Unicode, and extra-segment forms; numeric IDs are positive `NonZeroU64` newtypes ([`reference.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-core/src/reference.rs#L336-L428), [`reference.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-core/src/reference.rs#L430-L612)).

Canonical identity is enforced at result construction. `validate_canonical_identity` rejects selector-bearing or noncanonical references except where the typed family explicitly permits the request, and the discovery engine's `canonical_identity` separately permits GitHub page references because they name distinct upstream pages ([`resource.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-core/src/resource.rs#L536-L575), [`discovery.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-core/src/discovery.rs#L1234-L1284)).

**Implication for Atlassian:** a native multi-site family needs an explicit `ResourceAddress` variant and validated site/object/child newtypes (or it must deliberately use an already-owned family, which would misstate ownership). Site identity must participate in the canonical reference so two sites cannot collide in reads, cache keys, mutation locks, Version Tags, or diagnostics. Any new aggregate/field/page cases must be exhaustive across identity validation, catalog, dispatch, discovery, and mutation routing.

### 5. Aggregates, Fields, and Creation Targets are separate resource contracts

The GitHub address model distinguishes read-only Aggregate and collection projections from authoritative Fields. `render::issue_aggregate` and `render::pull_request_aggregate` render metadata and body content, but include canonical `title`, `body`, and child references. Comments/reviews/diff files are separately addressable, and aggregate output explicitly links each child ([`render.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-sources/src/github/render.rs#L45-L195)).

`GithubSource::read_resource` resolves the typed address, authorizes the allowlisted repository, renders the source-owned representation, applies line selectors, and computes mutability with `field_mutability`. Aggregate and collection reads are not made mutable merely because some displayed fields can be changed ([`github/mod.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-sources/src/github/mod.rs#L1112-L1162)).

GitHub Field mutation parsing accepts only existing issue/PR title, body, and stable conversation-comment resources; Aggregate, collections, reviews, inline review comments, and diff projections return unsupported mutation. Creation parsing accepts repository `new` and issue-style conversation `comments/new` targets for issues and pull requests ([`mutation.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-sources/src/github/mutation.rs#L22-L218)). Creation documents have strict source-specific frontmatter: issue creation requires `title`, PR creation requires `title`, `head`, and `base` with optional `draft`, and comments require their body shape ([`mutation.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-sources/src/github/mutation.rs#L769-L1017)).

**Implication for Atlassian:** do not model one rendered Aggregate as a replacement document for all upstream values. Identify which values are authoritative Fields, which projections are read-only, and which `/new`-like references are true Creation Targets. Stable child identity and parent ownership must be part of the typed address contract. The source-specific creation grammar, required fields, and returned canonical identity are design decisions requiring evidence; GitHub's frontmatter is not a reusable default.

### 6. Search and continuation have a source-neutral engine but source-specific page semantics

`DiscoveryAdapter` accepts a `SearchTarget`, pattern, options, and cancellation guard. A source returns `SearchSourceResult` containing an engine, canonical `SearchRecord`s, diagnostics, and an optional typed source continuation; the core `DiscoveryEngine` normalizes records/diagnostics, renders a bounded canonical document, pages it under lower-only limits, and retains omitted content as an artifact ([`discovery.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-core/src/discovery.rs#L19-L40), [`discovery.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-core/src/discovery.rs#L301-L467), [`discovery.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-core/src/discovery.rs#L646-L767)).

When inline output overflows, the artifact continuation must win because it is the only route to omitted bytes. If a source also has an upstream continuation, the engine retains it in the artifact as a typed `Continuation:` trailer and exposes `sourceContinuationReference` separately. The same rule applies to search; it is codified in ADR-0006 ([`read.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-core/src/read.rs#L105-L224), [`discovery.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-core/src/discovery.rs#L770-L833), [`0006-source-continuation-alongside-recovery.md`](https://github.com/dwalleck/resourcefs/blob/main/docs/adr/0006-source-continuation-alongside-recovery.md#L1-L2)).

GitHub's source-specific implementation fixes 100 objects per upstream page, follows at most 10 pages per logical operation, parses `rel="next"`, confines every target to the same API origin and repository endpoint family, and creates typed `<collection>:page:<n>` references. Collection reads carry one continuation. An Aggregate may fetch several collections; it writes every remaining collection page as a `Continuation:` line and deliberately has no single next page of its own ([`github/mod.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-sources/src/github/mod.rs#L41-L150), [`github/mod.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-sources/src/github/mod.rs#L474-L552), [`github/mod.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-sources/src/github/mod.rs#L724-L923)). The Link parser is strict about malformed shape and lenient about relation spelling; this follows the standard relation model in RFC 8288 ([`github/mod.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-sources/src/github/mod.rs#L1278-L1355); [RFC 8288](https://www.rfc-editor.org/rfc/rfc8288)).

**Implications for Atlassian:**

- A single site/collection can reuse `SearchSourceResult` and typed source continuations, but the cursor/page grammar and link validation must be source-owned.
- A multi-site search fan-out is not represented by the current `SearchTarget`, which names one optional Path Reference. The source must either define a canonical aggregate that owns all site results and emits multiple continuation lines, or keep searches site-scoped; silently searching every site would conflict with the primary-root/non-union and explicit-target conventions.
- Any collection with several independent cursors has the same Aggregate issue GitHub solves with textual continuation lines. The one `continuationReference` field is intentionally not a multi-cursor protocol.
- Core result normalization sorts by canonical reference and line, so site identity must be in the canonical string for deterministic cross-site output.
- Remote `glob` is not a fallback for discovery: HTTPS and GitHub both reject it as unsupported. A new source should expose only the enumeration it can prove and bound.

### 7. Grants, Version Tags, and commit-time revalidation are independent layers

Profile grants are operation-specific booleans (`create`, `update`, `delete`) with absent values defaulting to false. A source kind declares the operations it supports, and nested GitHub repository grants must be subsets of the source grants. Configuring a source or repository does not grant mutation ([`grants.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-sources/src/configuration/grants.rs#L3-L81), [`model.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-mcp/src/profile/model.rs#L1423-L1477)).

Core `MutationEngine` validates the request matrix, resolves a `MutationTarget`, validates source-native content before I/O, serializes locks by `source_key + canonical_reference`, loads current state, starts commit ownership, calls the adapter, and rejects outcomes incompatible with the target mode. It requires `operationId` for non-idempotent Creation Targets, and the Path Session journal replays an identical completed operation but rejects reuse for a different target/content ([`mutation.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-core/src/mutation.rs#L946-L1292), [`mutation.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-core/src/mutation.rs#L1309-L1601), [`session.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-core/src/session.rs#L649-L763)).

A `VersionTag` is exactly `sha256:` plus 64 lowercase hexadecimal characters and is derived from authoritative content bytes; it is not an mtime, counter, or upstream numeric version ([`version.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-core/src/version.rs#L5-L50)). Hashline edits additionally carry the exact read header and typed version selector, and the Path Session records displayed ranges. `resolve_seen` requires exactly one matching Resource/version snapshot and rejects an ambiguous short prefix ([`mutation.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-core/src/mutation.rs#L160-L279), [`session.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-core/src/session.rs#L1412-L1464)).

GitHub uses `MutationTargetMode::AuthoritativeText` for Fields. Its `load` fetches an uncached field snapshot and hashes the rendered authoritative value. At commit, it fetches again, compares the expected Version Tag immediately before PATCH, sends the minimal payload, validates returned identity/content, invalidates the GitHub cache, and returns the response-derived Version Tag. Ambiguous transport or malformed post-write responses are `Unknown`, requiring reconciliation; the adapter never automatically retries a mutation ([`mutation.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-sources/src/github/mutation.rs#L338-L457), [`mutation.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-sources/src/github/mutation.rs#L1019-L1150)).

**Implications for Atlassian:** decide the grant hierarchy (source/site/project/object/Field) and make child grants subsets of parent grants rather than adding an adapter-enabled flag. Decide what exact authoritative projection is hashed for each Field, how null/empty values render, and whether the upstream returns an authoritative post-write value or the submitted text. If sites share an adapter and source key, the canonical reference must still distinguish sites; otherwise locks and cache invalidation can conflate independent resources. Creation targets require an operation-ID/reconciliation contract regardless of upstream idempotency confidence.

### 8. Canonical upstream validation prevents identity confusion

GitHub's wire structs model only fields the adapter renders or validates: IDs, numbers, titles/bodies, authors, timestamps, URLs, PR markers, parent URLs, review/diff fields, and pagination metadata. JSON decode reports bounded path-aware errors ([`wire.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-sources/src/github/wire.rs#L1-L127)).

Before rendering, GitHub validates positive IDs, object number equality with the Path Reference, author shape, unique IDs in collections, required listing fields, and comment/review parent URLs. It rejects an issue endpoint response that is actually a pull request and rejects comments whose repository-wide endpoint response belongs to another issue/PR. Mutation responses also validate object URL/repository identity and stable IDs ([`github/mod.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-sources/src/github/mod.rs#L1357-L1559), [`mutation.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-sources/src/github/mutation.rs#L1175-L1235)).

**Implication for Atlassian:** upstream JSON is untrusted input. A site/object/child response must be checked against the requested typed identity and expected parent before it becomes a Resource, search record, cache entry, Version Tag, or mutation receipt. GitHub's exact fields and URL forms are not portable, but the validation obligation is.

### 9. Degraded-source diagnostics are source-level today

`ProbeRunner` runs configured probe adapters concurrently under a five-second run deadline, emits records in profile order, and marks missing/failed optional probes `Degraded` while required failures are `Failed`. `LaunchPlan::degraded_ids` permits optional degraded records and rejects required/unavailable or unsupported records ([`probe.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-sources/src/probe.rs#L139-L305), [`launch.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-mcp/src/launch.rs#L58-L85)).

The probe report exposes `{id, kind, required, state, diagnostic}` and redacts diagnostics through the profile redactor ([`report.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-mcp/src/profile/report.rs#L7-L91)). The HTTP substrate keeps configured degraded origins apart from the healthy allowlist and refuses only matching URLs as `source_unavailable`; a healthy origin sharing a host can continue serving ([`http/mod.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-sources/src/http/mod.rs#L546-L565), [`http/mod.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-sources/src/http/mod.rs#L798-L814)). `SourceCatalogEntry` can carry a degraded reason, but the current HTTPS and GitHub catalog implementations provide `None`, and the compiled registry has no independent per-site status object ([`catalog.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-sources/src/catalog.rs#L21-L59), [`https.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-sources/src/https.rs#L132-L140), [`github/mod.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-sources/src/github/mod.rs#L1194-L1210)).

**Implication for Atlassian:** define whether `required` applies to the complete multi-site source or to each site. If sites are children of one source, the existing probe/report shape cannot identify a partially degraded site without a deliberate extension. The behavior must preserve the current promise: optional unavailability leaves ResourceFS active, and only references owned by the unavailable authority fail. It must also decide whether site health appears in diagnostics/catalog or only affects resolution.

### 10. Deterministic fakes and live smoke rows are complementary proof

The permanent GitHub adapter contract builds a local TLS listener with a router closure, injects a host lookup resolving the fixture host to loopback, and trusts only a fixture CA. It covers zero-egress creation-target reads, stable Aggregate/Field content, repository allowlist precedence, status classification, rendered-resource search, bounded collections, typed page continuation, Link confinement, object/parent validation, ETag cache behavior, retries, and diff-file indexing ([`github_adapter_contract.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-sources/tests/github_adapter_contract.rs#L89-L155), [`github_adapter_contract.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-sources/tests/github_adapter_contract.rs#L191-L232), [`github_adapter_contract.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-sources/tests/github_adapter_contract.rs#L517-L625)).

The GitHub mutation contract uses a stateful `Arc<Mutex<GithubState>>` router. It changes titles/bodies/comments, counts PATCH/POST operations, can return malformed/truncated/wrong-object/wrong-parent statuses, and is used to prove uncached compare-before-write, serialization, cache invalidation, strict creation documents, payload minimality, operation recovery, and unknown outcomes ([`github_mutation_contract.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-sources/tests/github_mutation_contract.rs#L28-L359), [`github_mutation_contract.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-sources/tests/github_mutation_contract.rs#L376-L741)).

The HTTPS credential contract uses unique sentinel credentials, positive wire controls, no-channel leak scans, and a trickled body for cancellation. The HTTP substrate contracts exercise source-neutral request types, bounded metadata/body handling, non-redirecting mutation requests, and header policy ([`https_credential_contract.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-sources/tests/https_credential_contract.rs#L1-L23), [`https_credential_contract.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-sources/tests/https_credential_contract.rs#L90-L162), [`http_substrate_contract.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-sources/tests/http_substrate_contract.rs#L1-L40)).

The live adapter rows are ignored by default. `github_live_smoke.rs` requires `GITHUB_TOKEN` and reads public `rust-lang/rust`, proving real repository Link shapes, page 11, Aggregate child projections, parent checks, wide diff-file indexing, ETag/304 stability, and search line attribution. `https_live_smoke.rs` requires `RFS_LIVE=1` and checks real reader-mode markup, raw/line projections, redirects, 404 classification, allowlist refusal, and search against the canonical URL ([`github_live_smoke.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-sources/tests/github_live_smoke.rs#L1-L12), [`github_live_smoke.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-sources/tests/github_live_smoke.rs#L99-L245); [`https_live_smoke.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-sources/tests/https_live_smoke.rs#L1-L10), [`https_live_smoke.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-sources/tests/https_live_smoke.rs#L74-L186)).

The full-stack `resourcefs-mcp/tests/stdio_live_smoke.rs` starts the real `resourcefs` binary, writes a strict profile with required GitHub and HTTPS sources, runs `check --probe`, then exercises catalog, Field read, Aggregate search, paginated collection, HTTPS read, and error categories over JSON-RPC stdio. `scripts/live-smoke.sh` sets `RFS_LIVE=1`, obtains `GITHUB_TOKEN` from `gh auth token` when absent, and runs ignored `live_` rows ([`stdio_live_smoke.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-mcp/tests/stdio_live_smoke.rs#L26-L178), [`stdio_live_smoke.rs`](https://github.com/dwalleck/resourcefs/blob/main/crates/resourcefs-mcp/tests/stdio_live_smoke.rs#L180-L317); [`live-smoke.sh`](https://github.com/dwalleck/resourcefs/blob/main/scripts/live-smoke.sh#L1-L25)).

**Implication for Atlassian:** a deterministic fake should model the adapter's wire contract, including state transitions and malformed/identity-confusion responses—not just return happy-path JSON. A live row is needed for any page/cursor/link shape, redirect behavior, default page size, parent URL, validator, or markup assumption a fake cannot establish. The live row must assert shapes and invariants rather than mutable upstream counts. A full-stack row is the proof that profile conversion, credential resolution, probes, registration, rendering, and tool-boundary categories work together.

## Reusable seams versus GitHub-specific assumptions

| Existing element | Reusable for a multi-site Atlassian source | GitHub-specific assumption that must not be copied blindly |
|---|---|---|
| `SourceAdapter`, `DiscoveryAdapter`, `MutationAdapter` | Capability-bearing source contract and exhaustive routing | GitHub's issue/PR split and supported mutation set |
| `HttpSubstrate` / `OriginAllowlist` / `AddressPolicy` | One bounded, policy-checked HTTPS client; credentials attached at egress | GitHub API host, headers, Bearer composition, or status meanings |
| `ProfileDocument` / `SourceProfile` / `ConfiguredSource` | Strict versioned registration and conversion boundary | One GitHub variant, one source-wide credential, one API base |
| `SourceCatalogMetadata` | Canonical grammar/example and mounted-family catalog | `issue://` and `pr://` labels |
| `PathReference` / `ResourceAddress` / validated newtypes | Parse once, canonicalize once, preserve identity in every result | `owner/repository`, positive numeric IDs, `:page:<n>` semantics |
| Aggregate + Field + Creation Target split | Keep authoritative mutation separate from rendered composition; return canonical creation identity | Issue/PR title/body/comments and GitHub frontmatter |
| `DiscoveryEngine` and source continuation fields | Bounded search/recovery and typed continuation propagation | RFC Link parsing, 100/page, 10 pages, repository endpoint-family checks |
| `MutationGrants`, `MutationTargetMode`, `VersionTag` | Explicit operation grants; exact content tags; commit-time revalidation | GitHub no-delete capability and response object-id checks as the exact policy |
| `ProbeRunner`, `ProbeReport`, degraded origins | Bounded startup probe and optional-source survival | Source-level required/degraded granularity for a multi-site source |
| TLS listener + stateful router + ignored live rows | Deterministic wire/state tests and real-upstream smoke | GitHub fixture routes, object JSON, API pagination and known public IDs |

## Design decisions required before implementation

These are decision points exposed by the existing code; this note does not choose an Atlassian API model:

1. **Address family and site identity:** native `atlassian://` (or another explicitly owned family), and the exact path component that makes the site canonical and unambiguous. Do not reuse `issue://`/`pr://` or generic `https://` for an object family the source owns.
2. **Profile cardinality:** one source kind containing a site list versus multiple source instances. The current profile rejects duplicate kinds, so multiple same-kind entries would require an intentional contract change rather than a second convention.
3. **Credential scope:** one credential per source, one per site, or one per HTTPS origin; how helper/environment references are represented and redacted; and whether credential failure degrades a site or the complete source.
4. **Authority/grant scope:** source/site/project/object/Field hierarchy, supported operations, nested subset rules, and whether any creation target is non-idempotent enough to require `operationId`.
5. **Projection taxonomy:** which Aggregate, Field, child, collection, and Creation Target variants exist; which values are independently authoritative; and the source-specific create document grammar.
6. **Canonical identity validation:** site/object/child identity fields, parent ownership checks, duplicate detection, malformed-response behavior, and the exact canonical reference returned after creation.
7. **Version semantics:** the authoritative projection to hash, treatment of null/empty/normalized values, whether the upstream supplies a trustworthy post-write representation, and the adapter's unknown-outcome reconciliation behavior.
8. **Continuation model:** site/collection cursor grammar, whether a collection's next page is a typed reference, how multiple site/collection cursors appear in an Aggregate, and whether a multi-site search is supported at all.
9. **Availability diagnostics:** source-wide versus per-site required/degraded state, catalog visibility, probe granularity, and how a healthy site remains usable when a sibling site is unavailable.
10. **Evidence gates:** deterministic fake cases for every identity/grant/commit/continuation invariant, an adapter-level live row for real upstream wire shapes, and a full-stack profile-to-stdio row if the source is exposed through the shipped binary.

## Unresolved and live-probe questions

The following cannot be answered from this repository and must remain explicit until an authenticated or public upstream probe supplies evidence:

- Which Atlassian resource families are stable enough to receive canonical Path Reference variants, and what parent/child identity fields can prove ownership?
- What authentication material and credential scope are required per site, and can one configured credential safely serve multiple sites?
- Which collections paginate, what continuation metadata is returned, and do different sites or collection families use incompatible cursor shapes?
- Which writes return authoritative representations, which are asynchronous/ambiguous, and what source-native conflict/version signal can complement ResourceFS's content-derived Version Tag?
- What output is lossless and bounded for Aggregates, Fields, and diffs/attachments, and what should be read-only versus mutable?
- Can a site be probed independently, and should one unavailable site degrade while others remain mounted?
- What redirects, API host aliases, response media types, validators, and parent URLs occur in real traffic, and do they fit the shared `HttpSubstrate` without weakening its policy?

A live probe must be read-only unless a separately approved mutation contract requires otherwise. It should record response shape, identity invariants, page/cursor transitions, validators, redirects, and error categories—not hard-code mutable counts. It must not put credentials in artifacts, diagnostics, or protocol output.
