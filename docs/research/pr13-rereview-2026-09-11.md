## What the re-review found

### R1. The repair introduced a regression in the account-link comparison · P2 · **fixed**

`route_matches` compared the supplied link's **decoded** segment against the
authority's **raw** prefix segment. Both sides of that comparison come from
`Url::path_segments`, which yields *serialized* segments, so for a custom
`apiBaseUrl` carrying an escaped byte — `https://ghe.example/GitHub%20Enterprise/api/v3/`
— the two could never be equal, and **every** account link (repository owner,
commit author, commit committer) failed, taking the whole read with it. The
pre-repair code compared serialized to serialized and worked. The prefix is now
compared as spelled, and only the route — whose expected segments are the
account's own login and slug — is compared decoded.

### R2. That fix was itself verified only by derivation · P2 · **fixed**

The fixture's only path prefix was `/api/v3`, which carries no escaped byte, so
the green gate passed **both** the broken comparison and the fixed one; the
regression could have returned silently. `efe74d6` adds
`immutable_commit_facts_accept_percent_encoded_deployment_prefix`, which reads a
`/GitHub%20Enterprise/api/v3` deployment through the real adapter, and proves it
discriminates: the decode-observed/raw-base mutant FAILS the row, the fix passes
it, and the file is restored byte-identically.
