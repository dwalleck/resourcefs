# Name the source's next page alongside artifact recovery

A bounded `rfs_read` or `rfs_search` result has exactly one `continuationReference`, and it must be the reference that reaches what was cut from the returned page: when a page overflows, that is the `artifact://` chain, and nothing else can reach the omitted bytes. A paginated source — a GitHub repository collection with a typed `:page:<n>` continuation — therefore had its own next page displaced whenever its first page overflowed, surviving only as a `Continuation:` line at the end of the retained artifact and as a trailer row in a retained search document. Both survive by design as the text-only fallback, but a client that never pages the artifact to its end never learns that upstream page 11 exists. The decision (rfs-jsx9) is a second optional field, `sourceContinuationReference`, on read and search results only — glob enumerates no paginated source — carrying the typed upstream continuation *exclusively* when `continuationReference` walks an artifact chain that would otherwise hide it; when the page fits, `continuationReference` already names the source's next page and the second field is absent, so every result that existed before is byte-identical. The client rule is therefore short: follow `continuationReference` until a result has none, then follow the `sourceContinuationReference` you were given. The field is additive and optional, so the Behavior Contract moves from 1.0.0 to 1.1.0 rather than to a new major. A list of continuations was rejected because one collection has one next page, and an Aggregate that composes several collections names each of their continuations in its text rather than pretending to a single next page; the MCP Resources mirror (rfs-ww6w) should expose collection pagination through the same typed continuations rather than a second cursor vocabulary.
