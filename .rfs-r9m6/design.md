# Design: Strict Server Profile and CLI

## Route and inputs

- **Route:** Empirical. `.rfs-r9m6/route.md` records unverified OS/runtime behavior, a new public CLI/configuration seam, and production-scale process/output risks.
- **Approved behavior set:** `.rfs-r9m6/spec.md` is authoritative. Its requester-approved Given/When/Then set requires: exactly one launch authority; a strict schema-version-1 profile; fail-before-startup validation; existing client-over-launch Workspace Root precedence; separate mutation grants; referenced secrets; direct argv with a minimal environment; bounded whole-tree command cancellation; lower-only limits/session/logging; static and probing `check`; deterministic `schema`; and no telemetry. The Decisions table defines the exact profile fields, ten source kinds, limits, reports, command roles, exit codes, and edge behavior. Approval is recorded there as the requester's verbatim `"Agree"` on 2026-08-20.
- **Delivery increments from the spec:** (1) strict model/schema and static validation; (2) source configuration and launch composition; (3) shared secret/command/process substrate; (4) check/probe/reporting; (5) logging/session/limit application; (6) compiled-binary and cross-platform acceptance.
- **Empirical premises:** `.rfs-r9m6/evidence.md` records PASS for P1–P6. serde 1.0.219 and schemars 1.0.4 express the closed tagged model; ordinary `Option<T>` admits explicit null and therefore cannot implement the approved null rejection; direct argv plus a cleared explicit environment preserves literals on POSIX and Windows; tokio 1.47.1 concurrently bounds both child pipes; Unix process groups and Windows Job Objects terminate resistant descendant trees. Independent oracles are `oracle_schema.py`, `oracle_environment.py`, `oracle_bounded_pipes.py`, `oracle_posix_tree.py`, and `oracle_windows.ps1`, with native Windows execution through `windows_evidence_runner.py`.
- **Existing seams reused:** `WorkspaceRootId`, `WorkspaceRootSet`, `TextLimits`, `SearchLimits`, `GlobLimits`, `OperationGuard`, `LaunchRootSource::Profile`, `FilesystemSource::new`, `SessionStore`, `CompiledSources`, and the client-root refresh path in `resourcefs-mcp::server`.

### Removed invariant sweep

The change is not purely additive: making CLI roots optional removes the old `serve --root` precondition. That precondition silently guaranteed at least one launch Workspace Root, prevented scratch-only startup, made relative references appear always resolvable, and made profile/CLI authority mixing impossible by absence. Once removed, an empty active Workspace set and two candidate launch authorities become possible. C2 requires exactly one declared launch mode, C5 keeps relative references unavailable without an exact active Primary Root, and C28 proves scratch-only serving cannot acquire the launch directory as implicit authority. Existing client-root replace-not-union and per-connection Path Session isolation remain safe because the design feeds the existing `LaunchRootSource` and root-refresh seams rather than adding a second root store.

## Claims

- **C1.** `resourcefs-core` and `resourcefs-sources` remain free of rmcp/clap, and `resourcefs-mcp` retains the only downward dependency on both lower crates and the protocol/CLI libraries.
- **C2.** The CLI exposes only `serve`, `check`, and `schema`, and `serve` accepts exactly one explicit profile or one-or-more CLI roots while resolving each authority from its specified base directory.
- **C3.** Every invocation uses the approved 0/2/3/1 exit class and exact stdout/stderr contract, with no telemetry or diagnostic bytes in MCP stdout.
- **C4.** The bounded profile loader accepts only schemaVersion 1 closed objects, rejects explicit null and malformed/oversized input before authority construction, and stays schema-consistent and panic-free.
- **C5.** Profile Workspace Roots reuse the existing canonical root set, hidden-default visibility, exact Primary Root, and client-replaces-launch behavior, including an empty scratch-only launch set.
- **C6.** Create, update, and delete grants remain independent false-by-default booleans, and every nested grant is a subset of the operations its source kind supports and its parent grants.
- **C7.** The source catalog accepts exactly one entry per selected kind, explicit required state, bounded globally unique IDs and claims, and rejects cross-entry collisions before serving.
- **C8.** HTTPS configuration admits only non-overlapping allowlisted HTTPS base prefixes with explicit private-network policy and safe credential-header references.
- **C9.** GitHub configuration admits only an HTTPS API base, explicit network policy, one referenced credential, canonical allowlisted repositories, and repository grants bounded by source grants.
- **C10.** SSH configuration requires one validated direct command and distinct exact host aliases with non-overlapping absolute remote roots, and remains read-only.
- **C11.** Document configuration requires converters with disjoint lowercase extensions, an explicit stdin/path input mode, and a validated direct command, and remains read-only.
- **C12.** Skill configuration requires distinct contained canonical root directories and supports only the approved source-level grants.
- **C13.** Rule configuration requires distinct contained manifest paths and supports only the approved source-level grants.
- **C14.** Memory configuration requires distinct stable names and distinct contained file-or-directory targets and remains read-only.
- **C15.** Vault configuration requires distinct stable names/directories and per-vault grants that are subsets of source grants.
- **C16.** Agent Export configuration requires a non-empty distinct contained manifest-path list and remains read-only until its compiled adapter is present.
- **C17.** Downstream MCP configuration requires unique server IDs and native-scheme claims plus a strict stdio-or-HTTPS transport, and rejects non-resource proxying and mutation grants.
- **C18.** Secret resolution accepts only environment or helper references, normalizes successful helper output exactly once, rejects invalid bytes/outcomes, and keeps resolved values opaque to formatting and serialization.
- **C19.** Validated commands execute argv directly with literal arguments, a cleared PATH/SystemRoot-plus-explicit environment, role-correct path/input behavior, and no recursive secret mapping.
- **C20.** The command executor concurrently bounds both pipes, time, input, and live-tree admission at exact-limit/one-over boundaries and returns only after releasing/reaping owned resources.
- **C21.** Unix timeout or cancellation terminates the owned process group, force-kills survivors within the one-second grace contract, and leaves no live descendant or pipe reader.
- **C22.** Windows timeout or cancellation terminates the owned Job Object, force-kills survivors within the one-second grace contract, and leaves no live descendant or pipe reader.
- **C23.** Every profile ResourceFS limit is positive and lower-only, exact binary ceilings succeed, one-over values fail rather than clamp, and objectBytes never exceeds sessionBytes.
- **C24.** Session configuration applies an elapsed 0–86,400-second TTL under one ResourceFS-owned cache child, with TTL zero cleaning session state at disconnect and no sibling deletion.
- **C25.** Logging defaults to bounded info-on-stderr, optional file rotation is serialized and contained, and every message is redacted before any sink write.
- **C26.** Static `check` performs exhaustive schema/path/grant/claim/environment/executable validation without network or mutation and emits one deterministic redacted `notProbed` report.
- **C27.** Probe `check` attempts every configured source once, reports the four runtime states exhaustively, preserves optional degradation, and exits unavailable for required failure or unsupported adapter.
- **C28.** Serving applies one immutable checked launch plan, supports profile Workspace Roots and scratch-only operation, and rejects every configured source kind lacking a compiled adapter before stdio starts.
- **C29.** `schema` emits one deterministic pretty draft-2020-12 document with the stable ID/title, descriptions, closed objects, and one trailing newline that agrees with deserialization.
- **C30.** Serving never reloads its profile, while independent later `check` or `serve` invocations reread the file and Path Sessions remain connection-isolated.
- **C31.** Operator JSON/schema/logging code stays in `resourcefs-mcp`, source configuration/secret/process code stays in `resourcefs-sources`, source-neutral limit/probe/secret types stay in `resourcefs-core`, and platform process FFI stays behind the sources process facade.
- **C32.** Every list nested under one of the ten Source kinds accepts at most 4,096 entries, succeeds at the exact ceiling, and rejects entry 4,097 during bounded decoding before authority construction.
- **C33.** No resolved secret reaches process diagnostics, logging stderr/files, static or probe reports, CLI diagnostics, or MCP protocol stdout.

## Non-goals and future work

### Permanent non-goals

- No interactive profile manager, discovery, layering, include files, or hot reload: version 1 has exactly one explicit immutable file.
- No dynamic Source Adapter plugins or fourth runtime registry: the binary's compiled catalog is authoritative.
- No telemetry or exporter dependency; diagnostics remain local and bounded.
- No remote ResourceFS transport in version 1.
- No downstream MCP tool or prompt proxying; such fields are rejected.
- No automatic command/probe retry.
- No profile grant over Session Scratch.
- No increase or clamp above a binary ceiling.
- Soft deletion, replication lag, and multi-tenancy are N/A: a profile is local immutable process policy, not a replicated record or tenant boundary.
